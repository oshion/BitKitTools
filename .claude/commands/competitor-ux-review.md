기존 tool 1개를 골라 실제 서비스 중인 경쟁 tool들을 조사하고, UI/UX 관점에서 우리 tool 대비 경쟁 tool이 더 잘하는 점(가시성, 색상 구분, 사용성 등)과 우리가 이미 더 잘하는 점을 정리해 개선 초안을 리포트로 만들어라.

## 이 스킬이 아닌 것 (중요 — 먼저 읽을 것)

`bitkittools-ai-automation-roadmap.md`에서 "경쟁사 페이지 구조 분석 스크립트"는 이미 보류 결정됐다 — 비공식 API/HTML 파싱에 의존하는 **자동화 스크립트**는 SERP 구조가 바뀔 때마다 깨지고 유지보수 부담이 크기 때문이다. 이 스킬은 그것과 다르다: 매주 자동 실행되는 파이프라인이 아니라, **사람이 그때그때 호출하는 1회성 리서치 세션**이며 Claude가 WebSearch/WebFetch로 직접 조사하고 그 자리에서 판단한다. 유지보수해야 할 파싱 코드가 없으므로 로드맵의 보류 결정과 충돌하지 않는다. 이 구분을 사용자에게 설명이 필요할 때 활용하라.

먼저 다음을 읽어라:
- `/CLAUDE.md`
- `src/lib/config/tools-config.ts` (전체 tool 목록 — slug/category/title/description)
- `docs/UI_GUIDE.md` (우리 디자인 시스템 — 색상, 컴포넌트 규칙, "AI 슬롭 안티패턴" 금지 목록. 경쟁 tool의 특징을 무비판적으로 베끼면 안 되는 이유가 여기 있다)
- `docs/screens/{대상 tool 화면명}.md` (해당 tool의 원래 기획 스펙)

## 배경 지식

- **이건 트래픽 지표가 아니라 정성 평가다**: `/report-review`는 GSC/GA4/Clarity 지표로 개선점을 찾지만, 이 스킬은 지표가 전혀 없어도(또는 지표와 무관하게) UI/UX 자체의 완성도를 사람의 판단으로 점검한다. 두 스킬은 서로 대체하지 않고 보완한다 — `/report-review`는 그대로 지표 기반으로 유지된다.
- **스크린샷 없이 판단해야 할 때가 많다**: 이 세션에 브라우저 스크린샷 도구가 없다면 경쟁 tool의 HTML 구조·본문 설명·이미지 alt 텍스트·리뷰/커뮤니티에서 언급되는 UX 특징에서 추론한다. `run` 스킬로 우리 사이트를 직접 띄워 스크린샷을 비교할 수 있으면 적극 활용한다. 확신이 없는 추론은 "~로 보인다/추정된다"로 명확히 표현하고 단정하지 않는다.
- **경쟁 tool의 카피/브랜딩을 그대로 베끼지 않는다**: UI/UX 구조나 패턴(레이아웃, 색상 활용 방식, 인터랙션)에서 아이디어를 얻는 것과, 문구·디자인을 그대로 복제하는 것은 다르다. 후자는 저작권/상표 리스크가 있으므로 제안하지 않는다.
- **우리 디자인 시스템과 충돌하는 제안은 걸러낸다**: 경쟁 tool이 예쁘게 보이는 이유가 `docs/UI_GUIDE.md`의 안티패턴(glass morphism, 그라데이션 텍스트, 보라/인디고 브랜딩, 균일한 rounded-2xl 카드 등)일 수 있다. 이런 특징은 "경쟁사가 이렇게 한다"는 이유만으로 제안하지 않는다.
- **한쪽으로 치우치지 않는다**: 경쟁 tool이 무조건 낫다고 결론 내리지 말 것. 우리가 이미 더 잘하는 부분(예: 광고 CLS 방지, 다국어 지원, 면책조항 명시, 로딩 없는 즉시 계산)도 반드시 함께 기록한다.

## Step 1: 대상 tool 선정

인자로 특정 tool slug가 주어졌으면 그 tool을 대상으로 한다. 없으면:

1. `data/competitor-analysis/log.json`을 읽는다 (없으면 `{ "analyses": [] }`로 취급).
2. `tools-config.ts`의 전체 tool 중 이 로그에 한 번도 등장하지 않은 tool이 있으면 그중 하나를 우선 선정한다.
3. 전부 한 번씩 분석된 상태라면 `lastAnalyzedAt`이 가장 오래된 tool을 선정한다.
4. 선정한 tool과 이유를 사용자에게 먼저 알린다 (다른 tool을 원하면 이 시점에 바꿀 수 있게).

## Step 2: 우리 tool의 현재 UI/UX 파악

- `src/components/tools/{slug}/{Tool}.tsx`를 읽고, 입력 폼 구조, 결과 표시 방식(색상 사용 여부, 강조 방식), 반응형 처리, 에러/검증 UX를 파악한다.
- `docs/screens/{화면명}.md`의 원래 기획 의도와 실제 구현이 일치하는지도 함께 확인한다.
- 이 tool이 속한 카테고리(`developer`/`travel`/`beer`/`baby`)와 핵심 사용자 의도를 한 줄로 정리한다 — Step 3 검색어 선정에 쓰인다.

## Step 3: 경쟁 tool 리서치

1. WebSearch로 이 tool과 동일한 기능을 제공하는 실제 서비스 중인 사이트를 찾는다 (예: "hydrometer temperature correction calculator online", "bac calculator free"). 상위 결과 중 광고성 리스트 페이지가 아닌 **실제 계산기/도구 페이지** 2~4개를 고른다.
2. 각 후보를 WebFetch로 가져와 다음 관점에서 살펴본다:
   - 입력 폼 레이아웃 (필드 개수, 라벨 명확성, 단위 전환 지원 여부)
   - 결과 표시 방식 (색상 코딩, 아이콘, 단계별 안내, 숫자 강조 방식)
   - 정보 밀도와 스크롤 구조 (계산기가 above-the-fold인지, 광고/콘텐츠와의 배치)
   - 모바일 대응 힌트 (반응형 메타태그, 별도 모바일 안내 문구 등 텍스트에서 확인 가능한 것)
   - 신뢰 신호 (출처 인용, 최종 수정일, 저자 정보 — YMYL 성격 tool이면 특히 중요)
   - 우리에게 없는 추가 기능 (계산 이력 저장, 공유 링크, PDF 내보내기 등)
3. 무엇을 확인했고 무엇을 확인하지 못했는지(예: 실제 렌더링된 색상은 HTML만으로 알 수 없음) 투명하게 기록한다.

## Step 4: 비교 분석

- 경쟁 tool이 우리보다 나은 점을 구체적으로 나열한다 (예: "결과값을 배경색 있는 박스로 감싸 안전/주의/위험 단계를 색으로 구분 — 우리는 텍스트만 굵게 표시").
- 우리가 이미 더 잘하는 점도 동일한 형식으로 나열한다 (예: "우리는 EN/KO 완전 이중언어 지원, 경쟁 tool은 영어 전용").
- `docs/UI_GUIDE.md` 안티패턴에 해당하는 경쟁 tool의 특징은 "참고하지 않음" 목록으로 별도 표기한다.

## Step 5: 개선 초안 작성

실행 가치가 있다고 판단되는 항목만 골라 아래 형식으로 작성한다 (실제 코드 변경은 여기서 하지 않는다):

```
### [UI/UX] 제목
- **근거**: (경쟁 tool 어디서 확인했는지, 구체적 URL/특징)
- **현재 상태**: (우리 tool의 관련 코드 위치, 현재 구현)
- **제안 변경**: (구체적으로 뭘 어떻게 바꿀지 — docs/UI_GUIDE.md 색상/컴포넌트 규칙 준수)
- **예상 효과**: (정성적 기대치 — 트래픽 지표 근거가 없으므로 "CTR N% 상승" 같은 수치를 지어내지 않는다. "체감 사용성/신뢰도 향상" 수준으로 서술)
```

## Step 6: 리포트 저장 및 로그 갱신

1. `data/competitor-analysis/{slug}-{YYYY-MM-DD}.md`로 Step 2~5 전체 내용을 저장한다 (디렉토리 없으면 생성).
2. `data/competitor-analysis/log.json`에 `{ slug, lastAnalyzedAt: 오늘 날짜 }`를 upsert한다 (기존 항목 있으면 날짜만 갱신).
3. 이 리포트는 `/report-review`가 만드는 `data/reports/`와 별개 산출물이다 — 혼동하지 않도록 파일 경로를 분리해 유지한다.

## Step 7: 사용자 보고 및 구현

Step 4~5 결과를 요약해 사용자에게 보고하고, 어떤 개선 초안을 진행할지 확인받는다.

사용자가 특정 항목을 승인하면, TDD(테스트 먼저 — UI 컴포넌트 변경은 `@testing-library/react`로 렌더링/동작 검증) → `npm run lint && npm test && npm run build` 검증 → 커밋 → PR → auto-merge 흐름으로 진행한다 (`gh pr create` 후 `gh pr merge --auto --merge`). CLAUDE.md rule 17에 따라, 단순 스타일 조정 수준을 넘어 화면 구조 자체가 바뀌는 규모라면 여기서 멈추고 `docs/screens/{화면명}.md` 갱신부터 사용자와 논의한다.
